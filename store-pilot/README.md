# Тимчасове обмеження production-пілота ilovesad.com

Окремий плагін магазину `ilovesad-wfpms-pilot`; фінансовий код універсального `wayforpay-multi-seller` не змінюється. Призначення — обмежена перевірка двох покупок до загального запуску. Installation/deploy і платежі потребують окремого погодження оператора.

## Політика

- Покупець — локальний WordPress user ID акаунта `trofym@ukr.net`. ID перевіряється за авторизованим користувачем сервера та за власником замовлення. Введені billing email/customer ID, order key, роль адміністратора або URL не надають доступ.
- Два локальні product ID: фізична «Тестова книга», 100 UAH, профіль ФОП Ніни; віртуальний «Тестовий вебінар», 100 UAH, профіль ФОП Ярослави. Production ID ще невідомі. Модуль не створює товари й не містить staging-ID або ID покупця за замовчуванням.
- Кожна позиція контрольного замовлення повинна мати точний ID зі списку; variation ID звіряється окремо, parent ID не дозволяє варіації автоматично. Чинні WooCommerce правила кількості, сум, продавця та фінансового snapshot збережені. Книга й вебінар різних продавців купуються окремо. Контрольний товар разом зі звичайним товаром відхиляється.
- Немає налаштувань, список порожній/не має двох ID або пілот вимкнений — нові покупки форку й повторні виклики його шлюзів заборонені. Налаштовані контрольні товари закриті для гостя й інших акаунтів, включно з оплатою старим методом.
- Звичайні товари, у тому числі без профілю форку, використовують чинні шлюзи та checkout. Це діє для гостя, іншого покупця й самого контрольного покупця. Модуль не перепризначає старі замовлення новому мерчанту.
- Classic/AJAX, Store API/Blocks та CRUD/REST створення order перевіряються серверними hooks. Зареєстровані WooCommerce шлюзи мають обгортки `process_payment()`: перед фіналізацією покупки й спробою, включно з retry/order-pay, під order mutex повторно перевіряються поточний user ID, власник, точні товарні ID та метод. Власні інтеграції магазину повинні отримувати шлюзи з реєстру `WC()->payment_gateways()->payment_gateways()`; module wrapper не є заміною шлюзу, створеного довільним PHP-кодом поза реєстром. Такі caller-и треба включити в інвентаризацію перед production.
- Callback, збережена видана карткова форма, підтвердження фактичного IBAN-надходження, refund/review та runner не залежать від поточного входу покупця чи прапорця пілота. Фінансові перевірки й одноразовий `completed` залишаються в основному плагіні.

## Налаштування через адмінку

1. Перед установленням погодити backup/rollback, перевірити акаунт і чинні checkout caller-и/MU-модулі магазину. Оригінальний WayForPay залишається active/enabled і власником `/wc-api/wc_wayforpay/`. Legacy ownership/import production ключів для пілота не потрібні.
2. Встановити та активувати **тимчасовий модуль до активації форку**. Потім встановити вже прийнятий основний ZIP `da2b88c`. Відсутність форку залишає модуль без checkout-дій; після появи форку за замовчуванням він блокує нові оплати форку і повертає звичайним кошикам чинний checkout. Не активувати форк у проміжку без модуля.
3. У меню **WooCommerce → Міграція WayForPay** штатно ввімкнути standalone. Не натискати імпорт, захоплення історичного callback чи завершення legacy-переходу. Новий маршрут `/wc-api/wfpms_wayforpay/` належить форку; історичний лишається оригіналу. Нативне збереження активного пілота відмовляє, якщо standalone не ввімкнений або legacy ownership уже передано форку.
4. Під час погодженої production-підготовки оператор створює два товари, налаштовує потрібні профілі й фіксує фактичні ID, типи, ціни та продавців. Нічого не переносити зі staging лише за збігом назв/ID. До відкриття пілота тримати нові товари draft/закритими для продажу.
5. **WooCommerce → Пілот WayForPay**: ввести локальний WordPress user ID `trofym@ukr.net` та два товарні ID через кому; після перевірки ввімкнути «Дозволити нові контрольні покупки» й зберегти. Сервер перевіряє `manage_woocommerce`, nonce, існування локального акаунта з цим email та продуктів. Порожній список можна зберегти; він не дозволяє жодної покупки форку. Email потрібний лише для валідації акаунта під час конфігурації, не для авторизації покупки.
6. До реальної оплати повторити staging-сценарії нижче. Не вимикати production general scheduler або чинний runner guard. Модуль не додає runner, не змінює TTL/строки старих покупок і не зберігає секрети.

## Вимкнення після пілота

Штатна кнопка **«Зупинити нові контрольні покупки»** у меню пілота з правами й nonce встановлює лише `enabled=false`, зберігаючи локальні ID. Вона не потребує існування товарів/акаунта для аварійної зупинки. Нові покупки й retry заблоковані, звичайний checkout працює, всі вже видані платежі й черга обробляються далі.

Не деактивувати фінансовий форк або видаляти його таблиці/ключі після видання платежів. Не відновлювати стару БД поверх нових надходжень. Тимчасовий модуль залишити активним із закритим пілотом до врегулювання платежів і погодженого загального запуску: він також зберігає штатний checkout інших товарів. **Повне вимкнення обмеження** — деактивація тільки `ilovesad-wfpms-pilot` у списку плагінів за окремим погодженим cutover. Це знімає тимчасову політику й повертає checkout-правила основного форку; перед цим потрібне загальне призначення продавців/способів оплати. Деактивація модуля сама не змінює ownership, фінансові записи чи callback/runner основного плагіна. Вона не є безпечним способом просто зупинити пілот.

## Staging-приймання

1. До налаштування/з порожнім списком: авторизований buyer, гість і інший акаунт не створюють order/purchase/attempt через форк; звичайні товари купуються старим способом.
2. Активний пілот: позитивні покупки кожного контрольного товару окремо; guest/other/admin з підставленим billing email, customer ID або order key не проходять серверну перевірку. Сам buyer зі звичайним товаром використовує чинний checkout без seller-assignment error.
3. Додатковий неузгоджений товар, інша варіація, зміна власника, книга+вебінар різних продавців і контрольний+звичайний кошик відхиляються без нового фінансового запису.
4. Перевірити Classic/Store API, створення через підтримуваний REST/CRUD, зареєстровані gateway `process_payment()` та browser order-pay/retry. Чужі повторні оплати не змінюють вже збережені attempt/reference/ключі. Неперевірені caller-и, які створюють конкретний gateway class самостійно, є блокером production-пілота.
5. Закрити пілот штатною кнопкою. Нові й повторні спроби не проходять навіть у buyer; а видані карткові форми/callback й нативне IBAN-підтвердження працюють. Runner дає рівно один `completed`; повтори не повторюють виконання. Синтетичний signed callback надсилати тільки для нових синтетичних staging references або ізольованого runtime, не для production платежів.
6. Звірити власника обох маршрутів, backup/restore, зміни CLI/FPM/OPcache і взаємодію з чинними store/MU checkout модулями. За порожнім списком пілот має бути закритий одразу після activation; не відкривати продажі до цього доказу.

Runtime-тести модуля виконуються окремим етапом існуючої CI-матриці в новому WP prefix `wfppilot_` зі своїми користувачами, двома синтетичними продавцями та новими IDs. Налаштування/standalone/закриття/IBAN-confirm викликаються нативними HTTP формами, не SQL/options операторською процедурою. Зовнішня sandbox або production оплата не входять до цих синтетичних доказів. Сервер у кодовому сеансі не змінюється.

Джерело підтримуваних hooks: [WooCommerce 11.1 Checkout](https://github.com/woocommerce/woocommerce/blob/11.1.0/plugins/woocommerce/src/StoreApi/Routes/V1/Checkout.php), [реєстр шлюзів WooCommerce](https://github.com/woocommerce/woocommerce/blob/11.1.0/plugins/woocommerce/includes/class-wc-payment-gateways.php).
