# WayForPay: відповіді на release-gate питання форку

**Перевірено:** 11.10.2026

**Межі:** тільки офіційна технічна документація та база знань WayForPay; тільки універсальний форк `wayforpay-multi-seller`. Клубні merchant-и, товари, production-магазини й реальна оплата поза межами.

**Підсумок:** документація частково звужує невідомі, але не закриває P01 і P02. Для P03 її достатньо, щоб описати обережну ручну звірку; вона не визначає повний ідемпотентний протокол повернення.

## P01 — повторні списання й `orderReference`

WayForPay описує `orderReference` як унікальний номер замовлення торговця. У Purchase також є відповідь `1112 Duplicate Order ID`. Це підтверджує, що торговець має забезпечити унікальність посилань і що повторний ID може бути відхилений, але документація не формулює гарантії «не більше одного успішного списання на reference» для всіх способів повторної оплати. [Purchase](https://wiki.wayforpay.com/en/view/852102), [коди відповідей](https://wiki.wayforpay.com/view/852131)

Є важливий виняток для перевірки: Purchase має `orderTimeout` — період, протягом якого можна повторно сплатити замовлення; після успішної оплати WayForPay може передати `repayUrl` для повторної оплати в межах `orderTimeout` або `orderLifetime`. Документація не пояснює, чи така оплата створює нову операцію з тим самим `orderReference`, як тоді розрізняти операції, і чи поведінка залежить від способу оплати. [Purchase](https://wiki.wayforpay.com/en/view/852102), [Purchase українською](https://wiki.wayforpay.com/ru/view/852102)

`CHECK_STATUS` шукає стан за `merchantAccount` + `orderReference` і описує один набір статусу/суми/`authCode`/`cardPan`; він також містить `refundAmount` як суму всіх повернень. `TRANSACTION_LIST` повертає записи за період із `transactionType`, `orderReference`, сумою, статусом і часом процесування, але схема не документує стабільного унікального transaction ID. Підпис callback включає `authCode` і масковану карту, але документація не гарантує, що `authCode` є стабільним ідентифікатором операції. [CHECK_STATUS](https://wiki.wayforpay.com/view/852117), [TRANSACTION_LIST](https://wiki.wayforpay.com/en/view/1736786), [Purchase callback](https://wiki.wayforpay.com/en/view/852102)

**Висновок для форку:** P01 залишається відкритим. Код уже генерує випадковий унікальний `orderReference` для спроби та повторно використовує збережену активну спробу. Це правильна база, але локальна ідемпотентність callback не доводить, що провайдер не може провести друге списання в сценарії `repayUrl`. Поточний фінансовий ключ квитанції `(merchantAccount, orderReference)` не може надійно зберегти два окремі надходження з тим самим reference. Потрібно або мати документовану гарантію WayForPay про один capture/унікальний transaction ID, або змінити модель та приймання так, щоб другий відмінний підписаний success з тим самим reference зберігався як окремий фінансовий факт для ручного review, без повторного виконання замовлення.

**Практична дія:** доки немає такого доказу, не задавати `orderTimeout`/`orderLifetime` для форку, не використовувати й не показувати `repayUrl`, і не випускати нову спробу, поки попередня не має визначеного результату. Проте документація не визначає default повторної оплати, якщо ці поля не передані; тому цей захід зменшує поверхню ризику, але не закриває P01 без тесту або контрактного підтвердження.

## P02 — ротація merchant SecretKey

Документація Purchase каже, що callback підписується merchant SecretKey, а WayForPay надсилає callback повторно до чотирьох днів або до правильної відповіді сервера. База знань показує, де власник може переглянути merchant login/secret. Документ `Merchant Edit` описує редагування реквізитів партнера та повертає поле `secretKey`, але не визначає ротацію API SecretKey самого магазину, перекриття ключів або ключ, яким підписуються callback-и вже створених оплат. Документація з оновлення ключів пРРО стосується ключа електронного підпису каси, а не merchant SecretKey, тому її не можна застосовувати до цього gate. [Purchase](https://wiki.wayforpay.com/en/view/852102), [merchant credentials](https://help.wayforpay.com/view/3342958), [Merchant Edit](https://wiki.wayforpay.com/view/853327)

**Висновок для форку:** P02 документацією не закритий. Форк має зберігати версію конфігурації/credential, з якою створена кожна спроба, і старий зашифрований ключ для перевірки її callback. Це забезпечує локальний доступ до ключів, але не визначає, чи WayForPay ще використовує старий ключ для пізнього callback після зміни ключа в кабінеті.

**Безпечна поведінка:** не перезаписувати використану конфігурацію; новий ключ зберігати як нову версію. Ротацію не вважати безпечною для незавершених оплат, доки не визначені провайдерська поведінка й приймальний тест. Чотириденне повторення callback — це документований строк повторної доставки невизнаного callback, але не документована гарантія повного строку життя всіх платіжних станів або строку, коли старий ключ лишається чинним.

## P03 — ручне повернення та доказ

У M-portal можна зробити повне або часткове повернення для карткових платежів, Google Pay, Apple Pay і Privat24; гроші повертаються на ту саму картку. Для повернення потрібен доступний баланс магазину. База знань вказує, що при недостатньому балансі повернення не виконається до його поповнення. [Повернення у M-portal](https://help.wayforpay.com/view/3342455)

API `REFUND` вимагає merchant, `orderReference`, суму, валюту, коментар і HMAC-підпис запиту. Описана відповідь має статус `Refunded`/`Voided` або `Declined`, причину й код; підпис відповіді формується з merchant, reference, статусу й reason code, а не із суми. Довідник статусів описує `RefundInProcessing`, зокрема при недостатньому балансі магазину. [Refund API](https://wiki.wayforpay.com/view/852115), [статуси платежів](https://help.wayforpay.com/view/3342475)

`CHECK_STATUS` віддає `refundAmount` як суму всіх повернень, але описана формула підпису відповіді включає merchant, reference, amount, currency, authCode, cardPan, transactionStatus і reasonCode — не `refundAmount`. Тому це поле придатне для звірки, але за цією специфікацією його не можна вважати окремо захищеним HMAC доказом суми повернення. Сам API також не документує у відповіді окремий refund transaction ID або idempotency key. [CHECK_STATUS](https://wiki.wayforpay.com/view/852117)

**Висновок для форку:** документація дозволяє визначити ручну SOP, але цього недостатньо, щоб сказати, що реалізація P03 закрита. Для внутрішнього журналу потрібен незмінний refund event із локальним idempotency key, автором/підставою, сумою/валютою, merchant/reference, доказом провайдера й подальшою звіркою M-portal/транзакцій. Невизначений timeout, `RefundInProcessing`, розбіжність суми або повторна дія переходять у review; не повторювати refund автоматично. Успіх означає підтверджений стан WayForPay та узгоджену суму, а не лише те, що локальний запит відправлено. У поточному форку автоматизації та внутрішньої форми для цього немає.

### Мінімальний доказовий запис refund

Зберігати без секретів і карткових даних: Woo order/purchase ID; seller/config version; merchantAccount та orderReference; пов'язаний receipt/attempt; локальний refund operation ID; запитану суму/валюту/причину; operator/actor і час; sanitized provider request/response fields та їх підписи або хеш доказу; provider status/reasonCode; cumulative refund amount зі звірки; посилання/ідентифікатор M-portal evidence; остаточне рішення. Не зберігати PAN, CVV, секретний ключ або повний payload із зайвими персональними даними.

## Рішення щодо трьох gates

| Gate | Що встановили офіційні документи | Статус |
|---|---|---|
| P01 — кілька списань на `orderReference` | Є вимога унікального reference, помилка Duplicate Order ID і повторна оплата через `repayUrl`; окремого transaction ID та гарантії «один successful capture на ref» у перевіреній схемі не знайдено | **Відкритий:** потрібна модель/перевірка для другого signed success на тому самому ref або чітка гарантія провайдера |
| P02 — ротація SecretKey | Callback може повторюватися до 4 днів; overlap/старий ключ при callback після ротації не описано | **Відкритий:** зберігати версії ключів; провайдерську поведінку не можна вивести з документації |
| P03 — повернення | Є M-portal/API, partial/full refunds, статуси і накопичений `refundAmount`, але немає refund ID/idempotency contract | **Процедуру можна визначити:** ручний review та звірка provider evidence обов'язкові; автоматичні retry не обґрунтовані |

## Метод і межі

Перевірено одинадцять сторінок офіційної документації/бази знань WayForPay, станом на дату вище. Джерела належать одному провайдеру й не є незалежною перевіркою фактичної поведінки платіжного середовища. Висновки про недокументовані гарантії означають лише, що їх немає в перевірених схемах; вони не доводять відсутності такої поведінки у provider backend. Оплату, повернення, запити до merchant API та зміни налаштувань не виконували.

## Реалізаційне продовження у форку

Після дослідження у схемі v5 `receipts` отримали поле `provider_reference`, окреме від локального `external_id`. Для WayForPay воно зберігає `orderReference`, а локальний SHA-256 `external_id` розрізняє відмінні підписані callback evidence. Callback із тим самим підписаним набором полів залишається ідемпотентним; відмінний підписаний `Approved` для того самого reference зберігається окремою квитанцією з класифікацією review. Перша прийнята квитанція та стан виконання не змінюються. Міграція зберігає старі receipts і заповнює `provider_reference` їхнім попереднім `external_id`.

Інтеграційна перевірка також змінює merchant SecretKey між створенням спроби й callback: локальний код перевіряє callback ключем незмінної config-версії спроби. Це перевіряє збереження старого зашифрованого ключа у форку, але не доводить, яким ключем WayForPay підписує callback після ротації. Тому P02 лишається зовнішнім gate.

P01 також лишається частково відкритим: рішення розрізняє різні підписані callback evidence, а не provider transactions. Два окремі capture з ідентичними полями протоколу нерозрізненні без додаткового provider transaction ID або гарантії WayForPay. P03 описаний як ручна звірка в M-portal; автоматичного refund API чи внутрішньої форми журналювання у форку немає. Кодова перевірка не зверталася до WayForPay, sandbox або реальних платежів.
