# Завершення навчальної покупки — перевірка 2026-10-11

## Узгоджений обсяг

Плагін відповідає за фінансове підтвердження, одноразове завершення навчального замовлення у `completed` і стандартні події WooCommerce. Чинна автоматизація FluentCRM обробляє подальші теги, листи та Telegram. Tutor і окрема інтеграція FluentCRM не є вимогами або блокерами форку. Автоматизації й серверні налаштування не змінювалися.

Універсальна ознака навчальної/цифрової послуги для цього сценарію — усі товарні позиції замовлення віртуальні. Категорії й конкретні ID магазину не зашиті у код. Наявність хоча б однієї фізичної або недоступної товарної позиції не дозволяє форку примусово завершити замовлення після оплати.

## Причина штатного processing

У [WooCommerce 11.1.0, WC_Order::needs_processing()](https://github.com/woocommerce/woocommerce/blob/11.1.0/plugins/woocommerce/includes/class-wc-order.php) типова позиція не потребує обробки тільки за одночасних `is_virtual()` і `is_downloadable()`. Тому віртуальна послуга без файла за замовчуванням отримує `processing` після `payment_complete()`.

База вихідного коду: `d3d95b024072ae5517f969c5e10ef6ebe552be92`. Репродукція змінює лише integration-тести, production-файли тотожні базі. Runtime: ізольований WordPress 7.0, WooCommerce 11.1.0, PHP 8.3, MariaDB 11.4 у GitHub Actions; Classic/Blocks × HPOS off/on. Локальний WSL має приблизно 444 MiB доступної пам’яті, заповнений swap і не має Docker; синтетичний runtime на staging не розміщувався.

### Відтворена поведінка бази

Test-only commit `90ddd2505e59fe766a41c1f2e0fcf81388bdcada`, [CI 38158653071](https://github.com/trofoz/Word-Press-Woocommerce/actions/runs/38158653071): 4/4 успішно виконали репродукцію. Це доказ старого `processing`, а не приймання вимоги `completed`.

У кожній комбінації журнал показує: картка — `processing`, нуль подій `completed`; ручний IBAN — `processing`, нуль подій `completed`. Повторний callback/підтвердження не повторили `payment_complete()`. Причина відтворена у runtime без production-секретів.

### Вузьке виправлення та регресії

`PurchaseExecutionService` змінює тільки результат `woocommerce_payment_complete_order_status` під час авторизованого runner-виклику підтвердженої платної покупки форку: `processing` → `completed`, якщо всі товарні позиції віртуальні. Фізична позиція, відсутній товар, порожній склад, безоплатне або некероване замовлення не підпадають під нове правило. Штатний `payment_complete()` зберігає стандартні дії WooCommerce; окремий виклик `update_status()` не додається. Схема БД, платіжні маршрути та версія конфігурації не змінені.

Фінальна матриця виконує, а не лише перевіряє синтаксис:

- `integration-wayforpay-callback.php`: віртуальна послуга з уже обчисленим native `needs_processing` завершується один раз; дубль підписаного callback/runner не повторює `completed` і `payment_complete`; невідповідність суми не завершує покупку. Фізичний, змішаний і некерований віртуальний orders зберігають `processing`.
- `integration-bank-receipt.php`: accepted → `completed`, по одній події; duplicate/conflict → нуль нових завершень; перша невідповідність → `review`/`on-hold`, жодної події завершення; фізичний IBAN → `processing`, нуль подій `completed`.
- Workflow запускає всі п’ять IBAN cases (`accepted duplicate conflict review physical`) у кожному з чотирьох jobs, разом із попередніми checkout, guard, legacy, refund та expiry регресіями.

Фінальний remote commit, Actions run, висновки кожного job, ZIP і SHA-256 зафіксовані у супровідному файлі пакета staging-приймання. Sandbox/реальна оплата не включені у цю синтетичну перевірку й лишаються неперевіреними.

## Передача staging-оператору

- Налаштування перелічених товарів залишити: навчальні `virtual=true`, `downloadable=false`; саджанці фізичні.
- Встановлювати лише пакет, прив’язаний до фінального перевіреного commit і SHA-256.
- На ізольованих тестових замовленнях перевірити картку, ручне підтвердження IBAN і роботу адресного runner: навчальна покупка стає `completed` один раз, фізична залишається `processing`.
- Повторити callback/банківське підтвердження: стандартна подія завершення не повторюється. Перший платіж із фінансовою невідповідністю лишається у review без `completed`.
- Для змішаного складу virtual+physical не очікувати автоматичного `completed`.
- Плагін не встановлює нові правила Tutor, теги, листи або Telegram. Чинна автоматизація споживає стандартні події.
- Сервер під час цієї задачі не змінювався. Production не перемикається. Після передачі пакета подальші виправлення обмежені відтвореними дефектами staging-приймання.
