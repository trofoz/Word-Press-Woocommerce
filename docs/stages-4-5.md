# Етапи 4–5: purchase storage та WayForPay

Дата: 10.10.2026. Реалізовано у форку після етапів 1–3.

## Етап 4 — зафіксована покупка

- Додано versioned InnoDB таблиці покупок, карткових спроб, надходжень і підписаних подій. Існуючі seller/config/category tables збережені; schema version піднято до 2.
- Класичне WooCommerce checkout серверно визначає одного продавця, закріплює конфігурацію при створенні замовлення та зберігає несекретний знімок через Woo CRUD order meta.
- Спроба оплати та callback використовують спільне блокування за site ID і Woo order ID, короткі транзакції та `SELECT ... FOR UPDATE`.
- Перед видачею форми та при прийманні успіху знімок фінансових умов звіряється повторно. CRUD-зміни фінансових полів order/items після початку платежу блокуються; службові metadata дозволені, якщо самі фінансові поля не змінилися.
- Зміна правил каталогу не перепризначає вже зафіксоване замовлення. Зміна товарного складу перед першою спробою дозволена лише після серверної перевірки того самого продавця.
- Нульова сума не проходить через картковий шлюз. Запис підстави й передача безоплатного замовлення штатному WooCommerce додані на етапі 6.

## Етап 5 — карткова оплата

- Додано класичний WooCommerce gateway «Оплата карткою», приховування непогоджених шлюзів для маршрутизованого кошика та автопостинг форми WayForPay через endpoint з HMAC-підписаним token.
- Запит підписується за полями офіційного Purchase контракту; кожна спроба має криптографічно випадковий `orderReference` і збережений scale валюти. Оновлення сторінки перевикористовує незавершену спробу.
- Callback приймається лише для відомої спроби та очікуваного мерчанта після перевірки HMAC і відповідності суми/валюти. Зберігаються отриманий рядок суми, нормалізована сума, валюта та класифікація; PAN, authCode, сире повідомлення й секрет не записуються.
- Перше точне `Approved` за відкритим замовленням фіксує надходження. Розбіжність, повторне успішне надходження, оплата закритого замовлення, `Refunded` чи `Voided` переводять покупку до ручного розгляду. ACK надсилається після commit.
- Callback не змінює Woo статус і не викликає `payment_complete()`. Прийнятий receipt передає виконання окремому runner етапу 6; збій не запускає сліпий повтор email/LMS/stock hooks.

## Відкриті межі протоколу та запуску

- **P01 — кілька реальних списань на тому самому merchant/reference:** офіційний Purchase контракт, доступний для цієї реалізації, не надає окремого transaction ID. Унікальність receipt обмежена `(merchantAccount, orderReference)`; інша підписана evidence для того самого reference створює review event, але автоматично не розкладається на кілька транзакцій. До комерційного запуску потрібне письмове підтвердження WayForPay щодо повторних captures та надійного ідентифікатора.
- **P02 — ротація підписувального ключа WayForPay:** спроба прив’язана до конкретної конфігурації й перевіряється її збереженим секретом. Підтримки keyring/періоду перекриття немає. Не ротувати ключ мерчанта, доки окремо не визначено та не перевірено поведінку callback після ротації.
- **P03 — refunds:** статуси `Refunded`/`Voided` створюють review evidence; повернена сума не виводиться, автоматичне повернення та бухгалтерське коригування не виконуються.
- Схема callback реалізована для JSON body за офіційним Purchase прикладом. Інша форма доставки payload потребує перевірки до ввімкнення мерчанта.
- У цій сесії PHP syntax lint і `git diff --check` пройшли. Тести не додавалися й не запускалися; інтеграція з WooCommerce, мерчант sandbox, concurrency та HPOS не перевірені.

Це локальна реалізація та не готовий платіжний реліз. Етап 6 описаний у [stages-6-7.md](stages-6-7.md); інтеграційне приймання з WooCommerce та sandbox WayForPay залишається окремим кроком.
