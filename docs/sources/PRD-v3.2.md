# PRD універсального форка WayForPay для WooCommerce

Версія 3.2 • 10 жовтня 2026 року
Перший магазин: Клуб «Закохані у сад».
Статус: доопрацьовані вимоги для технічного планування. Бізнес-рішення частини II потребують окремого погодження перед запуском Клубу.

# Частина I. Універсальний форк

## Мета та результат

Плагін дозволяє одному магазину WooCommerce приймати оплату для довільної кількості продавців без зашитого в код обмеження двома профілями. Система визначає продавця за категоріями товару або ручним вибором адміністратора й спрямовує оплату на його мерчант WayForPay чи IBAN.

В одному кошику та замовленні допускаються лише товари одного продавця. Покупець обирає серед доступних цьому продавцю способів «Оплата карткою» та «Переказ на рахунок». Продавця визначає система. Кілька товарів одного продавця дозволені базовою політикою; додаткові обмеження конкретного магазину описуються у його впровадженні.

Документ має дві частини. Частина I визначає універсальний форк та критерії його випуску. Частина II визначає конфігурацію, інтеграції й окреме приймання магазину Клубу. Успішний випуск бази не означає автоматичної готовності магазину до запуску.

## Погоджені рішення

| Питання | Рішення |
|---|---|
| Кількість продавців | Довільна, без зміни коду при додаванні профілю |
| Призначення продавця | Автоматично за категоріями; ручний вибір має пріоритет |
| Змішаний кошик | Додавання іншого продавця блокується; наявний кошик зберігається |
| Способи оплати | WayForPay та ручний переказ на IBAN відповідного продавця |
| Фінансові умови | Фіксуються до видачі платіжної форми або банківських інструкцій |
| Повторні надходження | Обліковуються окремо; можливі переплати розглядає оператор |
| Виконання замовлення | Факт оплати зберігається незалежно від результату виконання |
| IBAN | Компактний журнал ручних підтверджень без банківського API |
| Нульова сума | Окрема підстава безоплатного виконання, без платіжної спроби |
| Інтеграції доступу | Перевірка та відновлення залежать від конкретного адаптера або ручної процедури |
| Приймання | Окремо універсальна база та впровадження у Клубі |

Нижче зафіксовані вимоги v3.1 з урахуванням рецензії та уточнень користувача. Невирішені бізнес-питання Клубу наведені в частині II; вони не вважаються погодженими цією редакцією.

## Межі першої версії

До обсягу входять профілі продавців, категорії, ручний вибір продавця товару, серверні перевірки кошика й замовлення, знімки фінансових умов, карткові платежі, IBAN-інструкції, облік підтверджених надходжень, ручний розгляд винятків, листи, журналювання та сумісна міграція оригінального WayForPay-плагіна. Класичний checkout, Checkout Blocks і HPOS входять до приймання бази.

Автоматичне розділення кошика, один платіж кільком продавцям, бухгалтерський облік, автоматична банківська звірка, нова інтеграція ПРРО та адаптери автоматичних підписок не входять до першої версії. База не обіцяє автоматичне відновлення доступів у довільній LMS, MemberPress чи іншому зовнішньому сервісі.

Плагін надійно фіксує фінансовий результат і запускає штатний процес WooCommerce. Перевірка зовнішнього виконання та його відновлення потребують названої інтеграції або задокументованої ручної процедури. У v1 достатньо збереженого стану, видимості проблеми оператору та контрольованого відновлення; загальний рушій автоматизацій не потрібний.

## Ролі та сценарії

Адміністратор налаштовує продавців, категорії, винятки товарів та міграцію. Уповноважений оператор підтверджує банківські надходження й розглядає проблемні платежі. У v1 ці повноваження може мати той самий адміністратор; вони перевіряються на сервері, а фінансові дії зберігають авторство. Покупець додає товари й обирає доступний спосіб оплати.

Основний сценарій: покупець оплачує замовлення карткою мерчанту визначеного продавця. Альтернативний сценарій: отримує його IBAN, а оператор після фактичного надходження підтверджує платіж. Створення замовлення чи заява покупця про переказ не є доказом оплати.

## FR 01 Профілі продавців

У WooCommerce має бути єдиний розділ керування продавцями з додаванням, редагуванням та архівуванням профілів. Кожен профіль має стабільний внутрішній ідентифікатор, який не залежить від назви чи порядку профілів.

Поля профілю:

- внутрішня назва для адміністратора;
- повне найменування отримувача;
- податковий ідентифікатор отримувача;
- IBAN та назва банку;
- шаблон призначення платежу з номером замовлення;
- параметри WayForPay, які потрібні чинному плагіну: обліковий запис мерчанта, секретний ключ, домен та інші необхідні поля після аудиту;
- окреме ввімкнення оплати карткою та переказу;
- стан активності профілю.

Секретні ключі доступні лише уповноваженим адміністраторам, приховані при відображенні, не потрапляють до клієнтських даних, листів або журналів. Збереження порожнього замаскованого поля не стирає наявний ключ. IBAN перевіряється на формат і контрольну суму; перед введенням у роботу отримувач перевіряється адміністратором.

Неповністю налаштований спосіб оплати недоступний покупцеві. Якщо у продавця немає жодного доступного способу оплати, оформлення замовлення з додатною сумою блокується зі зрозумілим повідомленням. Для дозволених нульових замовлень діє FR 16. Автоматичне спрямування до іншого продавця заборонене.

## FR 02 Категорії та визначення продавця

Адміністратор прив’язує категорії WooCommerce до продавців. Категорії зіставляються за їхніми ідентифікаторами; назви, товарні ID та бізнес-імена конкретного магазину не зашиваються в код.

Дочірня категорія успадковує правило найближчої налаштованої батьківської категорії, якщо не має власного правила. Для кожної категорії товару визначається її ефективне правило.

Алгоритм:

1. Якщо у товарі вручну вибрано продавця, використати його.
2. Інакше зібрати продавців із ефективних правил усіх категорій товару.
3. Один унікальний продавець — успішне визначення.
4. Більш ніж один унікальний продавець — конфлікт, який потребує ручного вибору або виправлення категорій.
5. Жодного продавця — товар не має визначеного продавця.

Неналаштована додаткова категорія не створює конфлікту, якщо інша категорія однозначно визначає продавця. Невизначений чи конфліктний товар не можна придбати; покупець бачить нейтральне повідомлення «Цей товар тимчасово недоступний для замовлення. Зверніться до нас». Адміністратор бачить точну причину та товар.

## FR 03 Поле продавця у товарі

У картці товару є поле «Продавець»:

- «Автоматично за категорією» — значення за замовчуванням;
- усі активні профілі продавців із налаштованих у магазині. Архівований профіль, уже призначений товару, відображається з попередженням; купівля блокується до виправлення.

Поруч показується фактично визначений продавець або причина конфлікту. Збереження товару з невизначеним продавцем можливе, але його купівля блокується. Потрібен список товарів із помилками для підготовки запуску.

У першій версії варіації успадковують продавця батьківського товару. Призначення різних продавців варіаціям одного товару не підтримується.

## FR 04 Кошик одного продавця

Перший товар визначає продавця кошика. Інші товари того самого продавця додаються звичайним способом. Додавання товару іншого продавця блокується до зміни кошика: наявні товари, їхня кількість та купони зберігаються.

Повідомлення:

> Товари в кошику й обраний товар продають різні продавці, тому їх потрібно оплачувати окремо. Оформіть товари в кошику, а потім придбайте обраний товар.

Дія: «Оформити замовлення» веде на checkout. Не очищати кошик автоматично й не замінювати його товари.

Перевірка виконується на сервері для всіх увімкнених шляхів додавання: сторінка товару, каталог, AJAX, пряме посилання, повторення замовлення та Store API, якщо він використовується. Самого приховування кнопки недостатньо.

Після спорожнення кошика його продавець скидається. Перед checkout продавець визначається повторно за поточними товарами. Якщо старий кошик став змішаним після зміни правил, оформлення блокується з проханням видалити товари одного продавця; система нічого не видаляє самостійно.

## FR 05 Оформлення та замовлення

Перед створенням замовлення сервер перевіряє кожен товар, однорідність продавця та, для додатної суми, доступність обраного способу оплати. Для нульової суми діє FR 16. При оформленні показується повне найменування продавця.

У замовленні зберігаються:

- стабільний ідентифікатор продавця;
- знімок найменування, податкового ідентифікатора та банківських реквізитів;
- ідентифікація мерчанта та конфігурації, використаних для платіжної спроби;
- поточний обраний спосіб оплати та історія способів у платіжних спробах і надходженнях;
- продавець кожної позиції для перевірки;
- ідентифікатори платіжних спроб та транзакцій;
- дата й джерело підтвердження оплати.

Секретний ключ не зберігається відкритим текстом у метаданих замовлення. Механізм збереження захищених версій конфігурації для старих платежів визначається під час технічного проєктування.

Зміни категорій, продавця товару або назв профілів не змінюють продавця вже створеного замовлення. Сторінка повторної оплати використовує продавця замовлення. Неможливість застосувати його платіжну конфігурацію не дозволяє оплату іншому ФОПу.

В адміністративному списку замовлень потрібні колонка та фільтр продавця. Продавець зафіксованого замовлення незмінний. До початку оплати фінансове редагування дозволене лише з повторною серверною перевіркою; після початку діє FR 14.

Єдина серверна перевірка перед початком оплати застосовується до таких шляхів:

| Шлях | Правило |
|---|---|
| Класичний checkout і Checkout Blocks / Store API | Перевірка товарів, продавця, фінансових умов та обраного шлюзу |
| Адміністративне замовлення та WooCommerce REST API | Ті самі правила перед видачею платіжного посилання чи IBAN-інструкцій |
| Сторінка повторної оплати та лист із посиланням | Використання збереженого продавця та умов, перевірка допустимості нової спроби |
| Повторення старого замовлення як нової покупки | Новий кошик проходить поточні правила каталогу |
| Підтримувані інтеграції створення разових замовлень | Спільна перевірка; непідтримуваний шлях не може видати платіж без валідного знімка |

Неповне адміністративне або API-замовлення можна зберегти як draft, але платіжне посилання, форму чи IBAN-інструкції не можна видати до остаточного розрахунку та перевірки.

Передані API-клієнтом seller ID, мерчант або знімок не є джерелом істини: вони перевіряються за серверними даними. Для старих замовлень діє окремий підтверджений історичний маршрут FR 12. Припущення про сумісність автоматичних підписок не входить до цієї матриці.

## FR 06 Оплата карткою через WayForPay

Покупець бачить один спосіб «Оплата карткою». Плагін вибирає мерчанта за продавцем замовлення, формує платіж і підписує його відповідною конфігурацією.

Перехід покупця на сторінку успіху сам по собі не підтверджує оплату. Карткова оплата підтверджується перевіреним підписаним серверним повідомленням WayForPay. Додатковий механізм звірки через API може використовуватися лише за окремо описаним і перевіреним контрактом; він не є вимогою v1.

При обробці повідомлення обов’язково перевіряються підпис, відповідність замовленню, мерчанту, сумі, валюті та платіжній спробі. Повторне повідомлення про те саме надходження не створює нового надходження й не запускає повторне виконання. Справжня друга оплата обробляється за FR 13, а відновлення після збою — за FR 15. Старий або суперечливий статус не скасовує вже підтверджену оплату без валідної події повернення.

Замовлення різних продавців не повинні мати конфліктів зовнішніх платіжних ідентифікаторів. Помилки спрямовуються до адміністративного журналу без секретів і зайвих персональних даних.

Підтримка автоматичних повернень перевіряється під час аудиту. Якщо вона вже є, повернення йде через мерчанта початкової транзакції. Якщо її немає, перша версія документує ручне повернення у відповідному кабінеті; кнопка автоматичного повернення не імітує виконання.

## FR 07 Переказ на IBAN

Покупець бачить один спосіб «Переказ на рахунок». Після оформлення реквізити продавця показуються на сторінці підтвердження, в особистому кабінеті та листі замовлення. Для гостя доступ до деталей замовлення залишається захищеним штатним механізмом WooCommerce.

Показати отримувача, податковий ідентифікатор, IBAN, банк, точну суму, строк оплати й призначення платежу. Номер замовлення обов’язковий у призначенні. Приклад: «Оплата за замовлення №1234». Остаточний шаблон налаштовує адміністратор. Повторний перегляд інструкцій не створює надходження й не змінює зафіксовані умови.

Замовлення очікує підтвердження банківського надходження. Сам факт створення замовлення, перегляду реквізитів або заяви покупця не підтверджує оплату і не відкриває платний доступ.

Уповноважений оператор використовує окрему дію «Підтвердити банківське надходження». Компактний журнал містить замовлення, продавця, ідентифікатор банківської операції, фактичний рахунок отримувача, суму, валюту, дату надходження, оператора та час підтвердження. Сервер перевіряє повноваження й захист дії від підробленого запиту. Ключ повтору — рахунок отримувача разом з ідентифікатором банківської операції; одне надходження не можна зарахувати двом замовленням, зокрема при одночасному підтвердженні.

Точне повне надходження на потрібний рахунок у межах строку може підтвердити оплату неоплаченого замовлення. Недоплата, переплата, інша валюта, інший отримувач, пізній платіж або друге надходження переводяться на ручний розгляд. Часткові надходження не сумуються автоматично для видачі доступу у v1. Розбіжність не перетворюється на доказ оплати продавцю; зафіксовані дані й рішення оператора зберігаються.

Після прийнятого підтвердження запускається штатне завершення платежу WooCommerce за FR 15. Звичайне редагування статусу замовлення не створює запису банківського надходження в журналі форку. Для фізичних товарів оплата не означає завершення доставки. Реакцію сторонніх інтеграцій на ручні зміни статусу перевіряють окремо при впровадженні.

Реквізити створеного замовлення залишаються його знімком. Закритий рахунок потребує контрольованого скасування або перевипуску неоплаченого замовлення; мовчазна заміна отримувача заборонена. Банківське API, завантаження виписок і бухгалтерські проводки до v1 не входять.

## FR 08 Членство та рекурентні платежі

Одноразові покупки доступу включаються до першої версії, якщо вони оформлюються через WooCommerce.

Перед впровадженням у конкретному магазині потрібно встановити, яка система створює регулярні платежі: WooCommerce, MemberPress, WayForPay або інша інтеграція. Якщо членство оплачується поза WooCommerce, цей плагін сам по собі не маршрутизує такі платежі; потрібне окреме завдання.

Для рекурентного сценарію обов’язкові незмінний продавець підписки, продовження через її початкового мерчанта, коректна обробка повідомлень і захист від повторної видачі доступу. Токени та регулярні списання не переносяться між мерчантами автоматично.

IBAN означає ручне продовження, якщо система підписок його підтримує. Не пропонувати IBAN для продукту, який технічно вимагає автоматичного списання. Сумісність і доступність цього способу для підписок визначаються аудитом та окремими приймальними перевірками.

## FR 09 Суми та сумісність

Знижки, податки, доставка й округлення зберігають стандартну логіку WooCommerce. До платіжної системи передається фінальна сума замовлення. Доставка й додаткові збори належать продавцю цього замовлення.

Перший випуск має підтримувати класичний checkout і Checkout Blocks. Для кожного потрібні реєстрація обох способів оплати, відображення продавця, повідомлення про конфлікт і серверна валідація. Обидва проходять приймальні перевірки. Працювати з замовленнями через WooCommerce CRUD; сумісність із HPOS підтвердити тестами.

Форк не запускає повторно штатне завершення оплати через повторний callback чи підтвердження IBAN. Резервування та списання залишків використовують механізми WooCommerce. Гарантії зовнішньої видачі доступу й листів визначаються перевіреними інтеграціями; порядок відновлення описаний у FR 15. Нульова фінальна сума обробляється за FR 16.

## FR 10 Життєвий цикл профілів і конфігурацій

Ідентифікатор продавця незмінний. Архівування припиняє нові покупки його товарів, але зберігає історію та обробку повідомлень вже створених платежів. Видалення профілю, пов’язаного із замовленнями або платіжними спробами, заборонене. Після архівування оплата старих неоплачених замовлень за замовчуванням заблокована; адміністратор може окремо дозволити її для такого профілю.

До першого оформленого замовлення помилку юридичної ідентичності можна виправити в профілі. Після першого оформленого замовлення юридичний отримувач незмінний: інша особа або податковий ідентифікатор потребують нового профілю. Виправлення написання назви тієї самої особи допускається зі збереженням історичних знімків.

Зміна IBAN, банку або merchantAccount того самого отримувача створює нову версію конфігурації після перевірки адміністратором належності реквізитів. Продавець і версія його платіжних реквізитів фіксуються при оформленні замовлення, до видачі інструкцій або форми. Нові оформлені замовлення використовують поточну конфігурацію. Неповний draft ще не є оформленим замовленням і не фіксує платіжне зобов’язання. Повторна оплата наявного замовлення зберігає його отримувача, мерчанта й IBAN; якщо вони недоступні, діє контрольований перевипуск. Ротація підписувального ключа того самого мерчанта не означає зміну отримувача. Платіжні спроби посилаються на конкретну версію. Ротація ключа потребує перевіреної процедури WayForPay: не припускати, що сервіс завжди підписує старим ключем. Старі версії зберігаються захищено протягом потрібного періоду обробки повідомлень. Заборонити витік ключів через REST, експорт профілів, логи та браузер.

Плагін не створює кабінети продавців, комісії чи взаєморозрахунки маркетплейсу. Усіма профілями керує адміністратор магазину.

## FR 11 Універсальний інтерфейс і локалізація

Назви способів оплати та повідомлення перекладаються. Українські значення за замовчуванням: «Оплата карткою» та «Переказ на рахунок». Текст для Клубу може використовувати «ФОП», але загальна логіка оперує продавцями. Призначення платежу підтримує лише явно дозволені підстановки номера замовлення; довільний код у шаблонах не виконується.

В адмініструванні потрібні пакетне призначення продавця товарам, фільтр за продавцем, перелік невизначених та конфліктних товарів. Категорії та профілі обираються з реальних даних магазину. Порожній список продавців не спрямовує платежі на тестового мерчанта. Оператор бачить перелік платежів на розгляді та незавершених дій, причину, підтверджені фінансові факти й історію власних рішень. Покупець після підтвердженої оплати бачить стан «Оплату отримано, виконання перевіряється», якщо виконання не підтверджене; нова вимога оплатити таке замовлення не показується.

## FR 12 Міграція оригінальної інтеграції

Імпорт чинних параметрів WayForPay виконується явною дією адміністратора з попереднім переглядом без відображення секрету. Повторний імпорт не створює дублікатів. Старі options зберігаються до завершення переходу.

Старі замовлення з payment_method wayforpay обробляються через збережений профіль старого мерчанта. Історичний маршрут застосовується лише до підтверджено мігрованих замовлень; для нових замовлень fallback заборонений. Старі orderReference зі схемою оригіналу не вважати достатнім підтвердженням платежу: додатково перевірити підпис, мерчанта, суму та валюту.

Нові платіжні спроби мають унікальне посилання, серверний запис очікуваної суми та валюти й зв’язок із замовленням. Обробка callback повинна мати захист від одночасних повторів, а не лише послідовних: перевірка та фіксація події виконуються атомарно або з надійним блокуванням.

## FR 13 Надходження та повторні оплати

Платіжна спроба, надходження й виконання замовлення — різні факти. Спочатку сервер зберігає спробу з очікуваними умовами; підтверджене надходження посилається на неї або на ручне IBAN-підтвердження. Для надходження зберігаються продавець, замовлення, джерело, зовнішній ідентифікатор, сума, валюта та час. Ідентифікатор унікальний у межах конкретного мерчанта для картки або рахунку отримувача для IBAN. Ідентичність карткового надходження визначається за перевіреним контрактом WayForPay; неперевірені API-поля не припускаються. Зміна обраного способу оплати не стирає історію попередніх спроб.

Повторне повідомлення про ту саму транзакцію оновлює її відомий стан і не створює другого надходження. Дві різні успішні спроби або картка й IBAN означають два надходження. Друге зберігається як можлива переплата для ручного розгляду; повторне виконання покупки не запускається. Для рішення щодо виконання одночасні підтвердження всіх способів оплати узгоджуються на рівні замовлення, а не лише одного callback.

Коли гроші підтверджені, але замовлення вже оплачене, скасоване, прострочене чи має підтверджене повернення, фінансовий факт зберігається й показується оператору. Він не відкидається через стан замовлення. Неперевірене повідомлення або повідомлення з неправильним підписом не стає підтвердженим надходженням.

Повернення пов’язується з конкретним надходженням. Повернення одного з двох платежів не означає автоматичного повного повернення покупки або припинення доступу. Якщо вплив на виконання неоднозначний, він потребує ручного рішення чи перевіреного адаптера. Записи надходжень не стираються для виправлення помилки; корекція залишає історію й автора. Автоматичні повернення переплат до v1 не входять.

Автентичне повідомлення про успішний платіж за відомою спробою з розбіжністю суми, валюти або очікуваних реквізитів зберігається як фінансовий виняток для ручного розгляду. Воно не підтверджує оплату замовлення й не запускає виконання. Повторне повідомлення не створює дубля винятку. Повідомлення з неперевіреним підписом не вважається доказом надходження.

## FR 14 Фіксація фінансових умов

Початок оплати — момент до першої видачі підписаної карткової форми або платіжного посилання чи до першої видачі IBAN-інструкцій. До цього моменту сервер зберігає знімок продавця, складу покупки з кількостями, суми, валюти, застосованих знижок, податків, вартості доставки та зборів. Якщо знімок не збережено, почати оплату не можна. Формування спроби та збереження знімка захищаються від одночасного редагування покупки: видана форма завжди відповідає одному узгодженому зобов’язанню.

Після початку оплати зміну цих фінансових умов блокують через інтерфейс, API та підтримувані інтеграції. Для зміни покупки у v1 використовують контрольоване скасування й нове замовлення з посиланням на попереднє. Старі спроби та надходження зберігаються і можуть потребувати ручного розгляду.

Примітки та контактні дані дозволено редагувати з дотриманням правил доступу. Номер відправлення та організаційні відомості доставки також можна доповнювати. Зміна адреси чи способу доставки, яка потребує перерахунку податків, доставки або фінальної суми, є фінансовою зміною й не може мовчки змінити знімок. Перед відправленням оператор має перевірити відповідність зміненої адреси зафіксованим умовам.

Зміна способу оплати між карткою та IBAN допустима лише за незмінних фінансових умов і доступної конфігурації продавця. Нова спроба не скасовує фактичної можливості оплати раніше виданого посилання. Скасування замовлення локально також не є підтвердженням закриття платіжної форми у WayForPay.

## FR 15 Підтвердження та виконання замовлення

Форк спочатку надійно зберігає підтверджене надходження, а потім запускає штатне завершення оплати WooCommerce без примусового завершення доставки. Фінансовий запис не відкочується через помилку листа, видачі доступу чи іншої подальшої дії. Підтвердження приймання callback не надсилається до надійного збереження фінансового результату.

У межах власного процесу плагін зберігає стани «очікує виконання», «виконується», «результат штатного завершення зафіксовано», «потрібна перевірка», час початку та зміни стану й діагностику без секретів. Завислий стан «виконується» виявляється та потрапляє до видимого оператору списку перевірки; поріг і спосіб перевірки визначаються технічним планом. Перерваний чи невизначений результат залишається видимим оператору. Такий стан не стверджує, що всі зовнішні системи завершили роботу. Після вже підтвердженої оплати нова оплата для цього замовлення не пропонується.

| Подія | Фінансовий результат | Дія щодо виконання |
|---|---|---|
| Перше повне валідне надходження для замовлення, яке ще очікує оплату, до строку | Оплату підтверджено | Запустити штатне завершення WooCommerce |
| Повтор повідомлення про те саме надходження | Наявний запис | Не повторювати завершення; зберегти незавершений стан, якщо він був |
| Інше надходження за оплачене замовлення | Можлива переплата | Ручний розгляд без повторного виконання |
| Пізнє надходження або надходження за скасоване замовлення | Гроші отримано, потрібен розгляд | Не відновлювати виконання автоматично |
| Збій після збереження оплати | Оплата залишається підтвердженою | Позначити необхідність перевірки/відновлення |
| Підтверджене повернення | Оновити відповідне надходження | Наслідки для доступу/доставки — за перевіреним контрактом або ручним рішенням |

Відновлення не означає повторний запуск усіх WooCommerce-подій. Перед повтором потрібно встановити, які дії вже відбулися. Автоматично або кнопкою відновлюють лише конкретну дію, для якої реалізовано перевірку результату й захист від повторного ефекту. Коли це неможливо, оператор звіряє результат вручну та фіксує рішення. Повторне списання залишків, розсилка всіх листів чи сліпий повтор усіх hooks заборонені.

Форк може відобразити відому помилку свого процесу чи під’єднаного адаптера, але не може виявити неповідомлену помилку довільного стороннього плагіна. Для кожної заявленої інтеграції окремо визначають спосіб перевірки доступу, відновлення, запобігання дублюванню й відповідального оператора. Універсальна база не обіцяє автоматично відкрити доступ у MemberPress чи іншій системі.

## FR 16 Замовлення з нульовою сумою

Якщо перевірена сервером фінальна сума дорівнює нулю, WayForPay не викликається, IBAN-інструкції не видаються, платіжна спроба й надходження грошей не створюються. Правила одного продавця, доступності товарів і дозволеної політики магазину залишаються чинними. Відсутність налаштованого платіжного способу сама по собі не блокує дозволене безоплатне замовлення.

Зберігаються продавець, склад покупки, нульова сума та її підстава — застосовані знижки/купони або дозволена нульова ціна. Після прийняття замовлення підстава і фінансові умови фіксуються. Замовлення проходить штатний безоплатний процес WooCommerce; інтеграції відрізняють безоплатне виконання від грошового надходження. Які товари дозволено виконувати безоплатно, визначається конфігурацією магазину й перевіряється при його впровадженні.

## FR 17 Строки, резерви та пізні надходження

Адміністратор налаштовує строк очікування окремо для картки та IBAN; обраний строк зберігається при початку оплати. Повторний перегляд сторінки не подовжує його. Базова політика v1: кінцевий строк, зафіксований при першому початку оплати, не змінюється при повторному перегляді чи зміні способу оплати. Запропонована додаткова політика — скорочувати його до ранішого зі строків двох способів — потребує окремого бізнес-рішення й не вмикається цією редакцією. Вплив строку карткової спроби на платіжну форму WayForPay перевіряється за документацією та можливостями мерчанта. Локальний строк і фактична доступність форми в провайдера не вважаються тотожними без перевірки.

Приймання оплати та завершення строку очікування узгоджуються під захистом на рівні замовлення. Одночасна робота callback, оператора IBAN і завдання скасування не може втратити надходження, повторно змінити залишки або ухвалити суперечливі рішення.

Після строку система припиняє пропонувати нову оплату цього замовлення та завершує його очікування. Звільнення резервів/повернення залишків узгоджується зі штатним механізмом WooCommerce без подвійної зміни запасів. Потрібний спосіб регулярного виконання перевірки строків документується та перевіряється при впровадженні.

Своєчасність надходження визначають за підтвердженим часом операції, а не лише часом отримання callback чи ручного підтвердження. Якщо на момент обробки замовлення вже скасовано або резерв звільнено, потрібен ручний розгляд навіть для своєчасної операції; невизначений час також потребує перевірки.

Усі callback продовжують прийматися після завершення строку, скасування або архівування продавця. Пізнє підтверджене надходження обліковується; оператор перевіряє актуальність покупки, доступність товару чи послуги та вирішує питання виконання або повернення. При відновленні фізичного замовлення залишки перевіряються заново. Плагін не приховує пізні гроші та не запускає виконання автоматично.

## Технічний підхід

Створити самостійний форк із власною назвою, slug, namespace та версією. Він замінює оригінальний плагін і не потребує його активності. Зберегти атрибуцію та GPL v3 з вихідного заголовка.

Джерело: https://github.com/wayforpay/Word-Press-Woocommerce
Базовий commit аудиту: b33c8bcb725cf02f8a546273596071024fa4a7ba.
Основний файл оригіналу: woocommerce-gateway-wayforpay.php.

У базовому коді один merchantAccount і ключ, старі властивості замовлень та примусове переведення успішної оплати в completed. Форк має замінити це вибором конфігурації замовлення, WooCommerce CRUD і стандартним payment_complete без примусового завершення доставки. Додати перевірку суми, валюти, платіжної спроби та повторних повідомлень. Оригінальний callback WC_wayforpay має оброблятися сумісним маршрутом для мігрованих старих платежів.

Відокремити відповідальність за профілі, визначення продавця, кошик і знімки, WayForPay, IBAN, надходження та виконання, Blocks, адміністрування й міграцію. Це логічні межі; окремий сервіс або фреймворк для кожної межі не потрібний. Не змішувати маршрутизацію з конкретними категоріями Клубу. Описати публічні hooks для майбутніх адаптерів підписок.

При виявленні активного оригінального плагіна показати адміністративне повідомлення та запобігти дубльованим шлюзам і конфліктним callback. До переходу нові платежі форку не запускаються. Після переходу повторна активація оригіналу не може позбавити вже створені платежі форку обробника: за потреби нові оплати призупиняються, але нові та історичні callback зберігають одного визначеного обробника кожний. Чинні стандартні BACS та сторонні шлюзи не вимикати мовчки: перед запуском адміністратор має явно обрати, які способи лишаються доступними. Для кошиків із призначеним продавцем непогоджені шлюзи приховуються, щоб не обійти маршрутизацію; це правило пояснюється в налаштуваннях.

Перед реалізацією перевірити актуальні офіційні вимоги WooCommerce та WayForPay щодо формування платежів, підписів, callback, рекурентів і повернень. Конкретні API-поля та назви статусів не припускати без перевірки.

Офіційні джерела для перевірки протоколу та інтеграції: [WayForPay Purchase](https://wiki.wayforpay.com/view/852102), [WooCommerce Payment Gateway API](https://developer.woocommerce.com/docs/features/payments/payment-gateway-api/), [WooCommerce BACS](https://woocommerce.com/document/bacs/). Точні схеми даних, блокування та механізм зберігання секретів описуються в технічному плані; цей PRD задає обов’язкову поведінку.

## Міграція та запуск

1. Зафіксувати версії WordPress, WooCommerce, PHP, checkout, HPOS та встановлених платіжних інтеграцій.
2. Підготувати резервну копію й ізольоване тестове середовище.
3. Явно імпортувати чинний мерчант у профіль його фактичного продавця з попереднім переглядом; повторний імпорт не створює дублікатів.
4. Налаштувати потрібні профілі та категорії; усунути невизначені й конфліктні товари.
5. Перевірити історичний маршрут замовлень і незавершених платежів за FR 12. Невстановлений історичний отримувач потребує ручної перевірки; поточні категорії не є доказом.
6. Перевірити обидва checkout, HPOS, надходження, строки, відновлення та конфлікт активації плагінів на тестовому сайті.
7. Перед запуском конкретного магазину пройти його окреме приймання, зокрема контрольні платежі відповідно до можливостей мерчантів.

Відкат після початку продажів зберігає обробку callback усіх задіяних мерчантів, надходжень і проблемних замовлень. Просте вимкнення форку не є достатнім відкатом. Коли повернення до попередньої версії несумісне з новими платежами, призупиняють нові оплати й зберігають обробку вже створених.

- Окремий звіт приймання Клубу, коли виконано частину II.

База готова до випуску після проходження її критеріїв. Готовність Клубу до реальних продажів визначається окремо в частині II.

65. Валідний підпис + відома спроба + неправильна сума → видимий фінансовий виняток, без підтвердження оплати й виконання замовлення; повтор не створює дубля.

## Межі готовності та перевірки

Підтримка довільної кількості продавців означає відсутність обмеження двома профілями, а не обіцянку необмеженої продуктивності. У першому випуску перевірити щонайменше три профілі з різними merchantAccount та IBAN.

Перед реалізацією зафіксувати цільові версії WordPress, WooCommerce та PHP за чинною офіційною документацією. Перевірити мінімальну заявлену й актуальну підтримувану конфігурацію. Не заявляти сумісність із усіма плагінами членства або підписок.

Автоматичні тести мають перевіряти критичні правила визначення продавця, захист кошика, знімки замовлень, платіжні підписи, невірні суми та повторні callback. Інтеграційні перевірки проводяться з WooCommerce; ручні сценарії покривають checkout, листи, IBAN та фактичні платежі. У звіті розділяти автоматичні, інтеграційні й реальні платіжні перевірки.

До релізу базової версії автоматичні рекуренти недоступні та не заявляються як підтримувані. Якщо цільовий магазин використовує їх зараз, запуск форка для цих товарів відкладається до створення і перевірки потрібного адаптера. Це не блокує розробку універсальної бази.

Перевірки виконання зовнішньої системи не замінюються тестовою заглушкою. У звіті прямо зазначати, де перевірено тільки контракт форку, де фактичний адаптер, а де потрібна ручна операція. У першій версії не потрібні повна бухгалтерія або універсальна черга відновлення всіх сторонніх подій.

# Частина II. Впровадження у Клубі «Закохані у сад»

## Конфігурація першого магазину

| Продажі | Початкове призначення |
|---|---|
| Книги й саджанці | ФОП №1 |
| Курси, членство в Клубі та вебінари | ФОП №2 |

Фактичні юридичні дані, merchantAccount, IBAN, категорії та товари зіставляються після перевірки. Вони не зашиваються в універсальну базу. Для цього магазину дозволено налаштувати назву переказу «Переказ на рахунок ФОПа».

## Рішення, потрібні до запуску Клубу

1. **Кількість послуг в одному замовленні.** Згідно з наданою редакцією v3.0, локальний ADR від 03.10.2026 передбачає одну послугу Ясі, одну позицію та кількість один. Водночас універсальна база дозволяє кілька товарів одного продавця. Потрібне явне рішення: зберегти додаткове обмеження Клубу чи замінити його. До рішення ADR не вважається скасованим; критерій №9 універсальної бази не є дозволом на багатопозиційне замовлення послуг Клубу. Якщо обмеження зберігається, реалізувати його як налаштовувану політику впровадження, без імен продавців у коді бази.
2. **Безоплатні покупки.** Універсальний нульовий шлях має окреме приймання для кожного дозволеного типу продукту. Згідно з наданою v3.0, у локальному документі готовності Club-zero відкладений; першоджерело потрібно перевірити перед впровадженням. Ця редакція не вмикає його: дозвіл і перевірка відповідної інтеграції потрібні окремо.
3. **Строки й умови IBAN.** Погодити строки для картки, банківського переказу та продажів із кінцевою датою. Перевірити актуальність локального правила оплати послуг фізособою з особистого рахунку; якщо воно чинне, включити його в інструкції та процедуру оператора.

Ці рішення стосуються впровадження Клубу й не блокують розробку універсальної бази.

## Інтеграції та використання наявної роботи

Перед запуском скласти коротку матрицю: тип товару → платіжний/безоплатний сценарій → система виконання → спосіб перевірки результату → спосіб відновлення → відповідальний. Для Tutor, MemberPress/BuddyBoss, CRM-листів, відправлення фізичних товарів і фіскалізації перевіряються саме встановлені версії та фактичні маршрути. Наявність статусу WooCommerce сама по собі не доводить, що доступ відкрито або лист надіслано.

Одноразові продовження через WooCommerce перевіряються як окремі замовлення. Якщо виявлено чинні автоматичні рекуренти, їх історичний маршрут зберігається; переведення на форк потребує окремого адаптера. Токени між мерчантами не переносяться.

Надана v3.0 описує проєкт `ilovesad-multi-merchant-checkout` як такий, що містить маршрутизацію, історію спроб, IBAN, відновлення й ізольовані сценарії перевірок. Перед переписуванням скласти перелік «повторно використати / адаптувати / не переносити» з конкретними файлами та їхньою перевіреною ревізією. Сценарії приймання є джерелом вимог до регресій; прив’язки до двох продавців, товарні ID та старі бізнес-припущення не переносяться автоматично. Наявні CI-докази не доводять працездатність нового форку.

## Підготовка й умова запуску

Потрібні звіт WooCommerce, установлені версії, перелік категорій і товарів, схема checkout, список інтеграцій доступу/підписок/фіскалізації та відповідальні оператори. Секрети вводяться лише в захищеному середовищі; для первинного аудиту робочі ключі не потрібні.

Використовувати ізольований тестовий контур. Надана v3.0 посилається на локальне правило, за яким синтетичні Docker-тести на production-host заборонені; перевірки такого типу виконуються в ізольованому GitHub Actions harness. Синтетичні прогони, перевірки встановлених інтеграцій і реальні контрольні платежі відображаються в звіті окремо.

Клуб готовий до запуску, коли пройдено критерії універсальної бази та всі застосовні C01–C15, погоджено відкриті бізнес-рішення, перевірено історичні платежі, визначено відповідальних і прийнято план переходу/відкату. Незастосовність кожного пропущеного критерію пояснюється в звіті. Власник бізнес-процесу приймає результат; користувач окремо дозволяє конкретний production-перехід. PRD та випуск ZIP самі по собі не є дозволом на запуск.

## Зміни редакції 3.1

Універсальні вимоги й приймання відокремлено від впровадження Клубу. Додано FR 13–17: надходження, фінансове блокування, обмежений контракт виконання/відновлення, нульова сума та строки. Уточнено юридичну ідентичність, ручне IBAN-підтвердження, усі підтримувані шляхи оплати й співіснування плагінів. Збережено підтримку довільних продавців, категорій, обох checkout і HPOS. Скорочення строку при зміні способу позначено як пропозицію; локальні джерела Клубу потребують перевірки. Критерії: 64 універсальні та C01–C15 впровадження.
