# Legacy callback: підготовка, приймання й повернення

## Обсяг і межа доказу

Прийнята база — `a64053e5520b91901ae20270225e9c53af268b38`; її синтетичне staging-приймання та IBAN A/B підтверджені оператором. Universal відсутній у цільовій конфігурації. Нові інтеграції Tutor/FluentCRM не потрібні. Для прийнятої оплати форку лише віртуальні товари отримують `completed`, фізичні/змішані — `processing`.

Цей сценарій виконується тільки на окремому disposable WordPress із тестовою БД. Не розміщувати синтетичний runtime на спільному з production staging. На чинному staging дозволене лише окремо погоджене приймання пакета магазину; наведені кроки не є дозволом міняти сервер. Секрети — виключно штучні тестові; реквізити та історичні конфігурації наявних замовлень не змінюємо.

Зовнішня sandbox-оплата, реальні підписи WayForPay, графік повторних callback провайдера, фінансове зіставлення справжніх старих замовлень і доступність production endpoint цими тестами не доведені.

## Що вже було в базі і що потребувало виправлення

| Механізм | У прийнятій базі | Необхідна зміна |
|---|---|---|
| Імпорт | Окремий nonce/capability handler; зберігає encrypted історичний config, старі settings лишаються | Відкрити вже наявні форми в standalone та початковому режимі |
| Прив’язка | Явна дія для неоплаченого pending/on-hold `wayforpay`; snapshot і config ID, без категорій як доказу | Правила прив’язки збережені |
| Reference | Додатний числовий ID або `ID_woo_w4p_ДОДАТНЕ_ЧИСЛО` | Нових форматів не додаємо |
| Історичний підпис | Тільки mapping.config_id, без підстановки current key | Правило збережене; відсутній ключ діагностується |
| Перемикання | Claim окремий від фінального switch; усі відкриті неоплачені legacy orders мають бути прив’язані | Показати switch також при чинному standalone |
| Callback без оригіналу | Mapped приймається форком; unmapped — HTTP 503, без фінансового запису | Доступна оператору WooCommerce-діагностика |
| Повернення ownership | Штатної дії немає | Мінімальна захищена дія; standalone й гроші форку збережені |

Межа історичної підтримки: mapping фіксує замовлення/продавця/config, а не повний перелік усіх колись виданих reference. Навіть автентичний `Approved` створює `needs_review` і не запускає виконання без рішення оператора. Невідомий callback не перетворюється на гроші лише за форматом ID. `transition_is_ready()` перевіряє відкриті pending/on-hold orders; це не інвентаризація вже скасованих, завершених, прострочених чи виданих провайдером платежів.

## Передумови окремого тестового хоста

1. Пакет форку з супровідного звіту, WooCommerce, оригінальний WayForPay pinned upstream `b33c8bcb725cf02f8a546273596071024fa4a7ba`; обидва активні. Зафіксувати їх commit/версії, активні плагіни, Classic/Blocks і HPOS.
2. Адміністратор із `manage_woocommerce`. Доступний `WFPMS_MASTER_KEY` у захищеному середовищі; не публікувати його. Окремі WP salts, БД й файлове сховище; вихідні листи/CRM/Telegram/webhooks вимкнені або спрямовані в sink. Жодних production credentials/товарів/замовлень.
3. `DISABLE_WP_CRON=true`: синтетичний runtime виконує лише адресну задачу форку. Загальну чергу Action Scheduler чи WP-Cron не запускати.
4. Резервна копія окремої БД й перелік синтетичних IDs. На shared staging створення synthetic historical merchant замінює глобальну конфігурацію оригіналу — тому там цей сценарій заборонений.
5. Початково власник legacy route — оригінал, форк — standalone, фінальний legacy-switch вимкнений. У наявному standalone жодні прямі `wp option update`/SQL для ownership не потрібні й не є операторською процедурою.

## Штатні дії через адмінку

1. На ізольованому хості: **WooCommerce → Налаштування → Платежі → WayForPay**. Задати виключно штучний історичний merchant і тестовий secret, зберегти штатною кнопкою. Не копіювати конфігурацію магазину.
2. **WooCommerce → Продавці**: створити окремий синтетичний історичний профіль із перевіреною юридичною особою/IBAN. Для нових платежів форку створити інший тестовий профіль із власним merchant/key. Призначити йому тестовий віртуальний товар. Точний slug сторінки профілів — `admin.php?page=wfpms-sellers`.
3. Через звичайну адмінку WooCommerce створити два pending замовлення `wayforpay` з цим тестовим товаром, сумою й валютою. Продавець історичного замовлення визначається окремим підтвердженням за джерелами, а не поточним призначенням товару. Третє неоплачене замовлення залишити неприв’язаним для негативного тесту.
4. **WooCommerce → Міграція WayForPay**, `admin.php?page=wfpms-legacy-migration`. Перевірити рядки «Власник історичного маршруту» й «Обробник оригіналу зареєстрований». Власник — оригінал. Standalone лишається активним для нових оплат.
5. «Попередній перегляд та імпорт»: обрати історичного продавця, звірити domain, підтвердити відповідність merchant юридичному отримувачу. Очікування: `imported`; старі settings збережені, ownership не змінився. Не обирати чинний продавець магазину для штучного імпорту.
6. «Підготувати обробку callback форком»: підтвердити передачу. Очікування: `callback_owned`; власник — форк, обробник оригіналу ще зареєстрований. Поки original active, неприв’язані reference передаються йому.
7. Для двох синтетичних orders у таблиці натиснути «Прив’язати та зафіксувати». Очікування: `order_migrated`, seller/config ID і фінансовий snapshot зафіксовані. Повторна міграція не переписує snapshot.
8. Спробувати «Увімкнути оплати форку» до врегулювання третього order: `transition_orders_unmigrated`, switch лишається вимкненим. Для позитивного сценарію завершити цей synthetic order через підписаний callback оригіналу; перевірити, що він не отримав purchase форку.
9. Повторити фінальний switch: `transition_enabled`; fork ownership активний, original gateway прихований для нових оплат, standalone flag збережений. До деактивації оригіналу виконати інвентаризацію нижче.
10. Лише в disposable runtime: **Плагіни → оригінальний WayForPay → Деактивувати**, або штатний `wp plugin deactivate wayforpay-upstream --path="$WP_PATH"` для назви CI fixture. У магазині slug потрібно прочитати в переліку плагінів. Не деактивувати форк чи WooCommerce.

## Runtime-приймання

| Сценарій | HTTP / результат | Операторський доказ |
|---|---|---|
| Numeric та suffixed mapped Approved, original inactive | 200, підписаний `accept`; pinned config; один receipt `needs_review` | Міграційний запис + «Платежі продавців»: review, order не completed |
| Точний повтор Approved | 200; ті самі receipt/events; нуль payment_complete/completed | Лічильники DB й адресний runner двічі |
| Прийнятий legacy Approved → Refunded/Voided → змінений Approved тієї самої спроби | Термінальна подія лишається фінансовою забороною; нуль payment_complete/completed; ownership return blocked | Справжні HTTP callback, штатний review, адресний runner; один receipt |
| Термінальна подія іншої, зайвої legacy-спроби | Чинна прийнята оплата першої спроби лишається підставою; completed один раз | Receipt-scoped acceptance; повтор callback/runner без нових receipt/events/завершень |
| Current config продавця змінився | Старий підпис перевіряється pinned config | Старі config/snapshot IDs незмінні |
| Історичний ключ недоступний | 400; нуль нових receipt; current original key не підставляється | Журнал `historical_config_unavailable` |
| Unmapped, original inactive | 503; жодного прийняття/нового purchase; тіло не є `accept` | Журнал `unmapped_reference_no_upstream`, order ID і reference hash |
| Непідтримуваний формат | 400, без оплат | Журнал `unsupported_reference` |
| Повернення без active upstream | `callback_unavailable`; ownership збережений | Сторінка міграції |
| Повернення з mapped review/pending/невідповідним ключем | `callback_release_blocked`; flags/фінансові факти збережені | Сторінка + `callback_ownership_return_blocked` |
| Повернення після reviewed accepted + done | `callback_released`; original owns, legacy-switch off, standalone on | Сторінка; snapshot/receipt/event IDs ті самі |
| Новий unmapped legacy callback після повернення | 200, обробляє оригінал | Новий synthetic order completed без purchase форку |
| Новий платіж форку після повернення | Власний merchant і `/?wc-api=wfpms_wayforpay`, completed один раз | Receipt accepted, runner, дубль callback/runner — нуль повторів |

Відсутній ключ відтворюється тільки fault injection у створеній для CI synthetic configuration. Не псувати шифротекст, salts чи master key на staging; зміна цієї конфігурації в тесті не є інструкцією міграції справжніх замовлень.

Повний відтворюваний виклик: `WFPMS_ADMIN_USER=… WFPMS_ADMIN_PASSWORD=… WP_PATH=… python3 tests/integration-http-legacy-operator.py`. Тест запускається після runtime/cart setup у workflow; створює лише synthetic fixtures. Адмінпароль брати з захищеного середовища, не копіювати в чат. Fixture setup записує тільки синтетичні settings оригіналу та тестові дані; **усі import/claim/map/switch/release і review дії виконуються через реальні nonce-форми HTTP**, не через пряму зміну ownership options.

## Зупинка й повернення standalone

Зупинити передачу при невідповідності merchant/отримувача, відсутньому ключі, незрозумілих reference, unmapped orders, неочікуваному HTTP, повторному receipt або completion. У магазині не змінювати вже зафіксовані історичні конфігурації задля проходження тесту.

1. Якщо ownership ще не передано — припинити підготовку; чинний standalone й оригінальний маршрут збережені.
2. Якщо ownership уже у форку — активувати оригінал. Він обробляє unmapped; mapped callbacks лишаються у форку до безпечного повернення. Не видаляти mappings/receipts і не змінювати options вручну.
3. Для повного повернення mapped покупок вони мають бути фінансово прийняті та виконані (`paid + done`, Woo paid). Для synthetic Approved: **WooCommerce → Платежі продавців → ручний розгляд**, перевірити суму/валюту/одержувача, зазначити підставу й можливість виконання; адресно виконати `wfpms_process_execution` з конкретним purchase ID. Повторний запуск не має повторити завершення.
4. У «Міграція WayForPay» натиснути **«Повернути callback оригіналу»**, підтвердити. Обов’язкові active upstream і повна відповідність його merchant/key усім pinned mapping configs. Незавершений review, refund/недостатня оплата, відсутній historical key або інший original key блокують повернення; форк треба лишити handler-ом цих платежів. Не підтверджувати спірну оплату тільки заради повернення.
5. Перевірити owner=original, original handler зареєстрований, legacy-switch off, standalone on, нові шлюзи/історія форку збережені. Нові issued платежі використовують власний callback; це не відкат БД. Після повернення legacy-повідомлення підкоряються правилам оригіналу й більше не записуються legacy-адаптером форку. Нові фінансові записи форку не видаляються.

## Коли можна деактивувати оригінал

Потрібні всі умови:

- Точна інвентаризація фактичних service URLs (`/?wc-api=WC_wayforpay` підтримується; aliases/інші endpoints окремо перевірити), reference formats, усіх незавершених provider-платежів і можливих пізніх статусів/повернень. Pending/on-hold список сам по собі недостатній.
- Для кожного ще можливого callback — доведені original order/seller/merchant і доступний відповідний historical key у pinned mapping. Якщо такого mapping немає, поточний механізм не гарантує автономної обробки; оригінал залишити активним до врегулювання/окремого рішення.
- Accepted migration UI cycle та mapped HTTP callback повторені на остаточному пакеті, обидва формати перевірені; маршрут реально веде в цей WordPress, fork owns. Окремо прийняти ручний розгляд legacy Approved: автоматичного завершення лише від історичного callback немає.
- Діагностика й оператор ручного review доступні; для 503 немає припущення про гарантовану повторну доставку провайдером. Невідомі повідомлення фіксуються в журналі, але їх payload не зберігається як фінансовий доказ: потрібне безпечне отримання даних і звірка з провайдером.
- Резервна копія та перевірений план повернення без втрати нових fork receipts. Якщо є mapped незавершені покупки або historical ключі відрізняються від current original, повне повернення ownership буде заблоковане: аварійний шлях — original active для unmapped + fork active для mapped.

Синтетичний CI доводить роботу механізму на окремому runtime. Деактивація оригіналу в магазині потребує inventory і окремого погодженого переходу; цей документ не дозволяє змінювати сервер/production.

Поточне рішення оператора: staging продовжує checkout і runner на `a64053e`; legacy ownership ще не передається. Перед окремим legacy-прийманням потрібно взяти виправлений пакет та його CI-звіт. Затриманий Approved не скасовує зафіксованих `legacy_Refunded`/`legacy_Voided` прийнятої спроби.
