# Остаточний контракт статусів оплати

Явне рішення користувача від 2026-10-11. Однакова політика для фізичних, віртуальних і змішаних покупок, керованих `wayforpay-multi-seller`. Цей документ замінює попередні правила завершення лише віртуальних товарів у readiness, FR11/FR15 копії PRD v3.2 та старих звітах приймання. Копія вихідного PRD і її provenance hash залишаються історичним джерелом.

| Ситуація | Статус WooCommerce |
|---|---|
| Покупець обрав картку, підтвердженої оплати ще немає | `pending` — В очікуванні оплати |
| Перша чинна карткова оплата прийнята й виконана | `completed` — Виконано, автоматично |
| Покупець обрав IBAN, надходження ще не підтверджене | `on-hold` — На утриманні |
| Адміністратор штатно підтвердив точне чинне IBAN-надходження й виконання завершилось | `completed` — Виконано |

## Межа плагіна

1. Підтвердження картки проходить перевірку підпису, історичної конфігурації, суми, валюти, спроби, строку та фінансового snapshot. До фінансового прийняття `completed` заборонений.
2. Для IBAN потрібна штатна авторизована nonce-дія підтвердження надходження. Вона зберігає bank operation ID, рахунок отримувача, суму, валюту, дату й оператора та приймає оплату за чинними фінансовими правилами. Вибір IBAN або ручне редагування Woo-статусу не створюють надходження.
3. Обидва канали використовують чинну надійну чергу й спільний одноразовий runner. Після durable commit runner повторно перевіряє чинність прийнятої оплати під order lock та викликає `payment_complete()` з кінцевим статусом `completed`. Додаткової ручної зміни статусу після підтвердження IBAN не потрібно. При паузі або збої виконання запис залишається pending/review для контрольованого відновлення; завершення до фінансового commit або обхід guard не допускаються.
4. Тип товару, virtual/downloadable та `needs_processing()` не визначають кінцевий статус прийнятої платної покупки форку. Проміжний `processing` для успішного виконання цієї покупки не потрібний. Некеровані замовлення та окремий безоплатний сценарій зберігають свої чинні правила.
5. Повтор callback, IBAN-підтвердження, запланованої задачі або конкурентний runner не створюють другого прийнятого надходження, `payment_complete`, переходу в `completed` чи `execution_done`.
6. Неприйняті фінансові винятки, пізні оплати та повністю повернені/недостатні прийняті надходження не запускають завершення. Чинна оплачена підстава при поверненні зайвого надходження враховується за фінансовим контрактом.
7. Стандартні події WooCommerce передають результат чинній автоматизації. Нові інтеграції Tutor/FluentCRM, теги, листи й Telegram не входять до цієї зміни.

## Приймання

- Картка: фізичний, віртуальний і змішаний склад починає з `pending`; після чинного Accepted та runner — `completed` рівно один раз, без переходу через `processing`.
- IBAN: ті самі типи складу після вибору лишаються `on-hold` без надходження/виконання; штатне підтвердження зберігає фінансовий запис, а runner переводить у `completed` рівно один раз. Повторне підтвердження не повторює виконання.
- Фінансовий виняток не завершує замовлення. Refund/recovery/legacy/expiry та конкурентні регресії зберігаються.
- Classic/Blocks × HPOS off/on перевіряються на остаточному кодовому commit. CI не замінює staging-приймання магазину або зовнішню sandbox-оплату.
