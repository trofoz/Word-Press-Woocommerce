Розділ 1, початкові аудити й [попереднє приймання навчальних покупок](educational-completion-acceptance-2026-10-11.md) є історичним зрізом; вони не доводять нову політику для фізичних товарів. Фінальний runtime-доказ і пакет надаються окремим звітом цього контракту.

- База перевірки: remote `d3d95b024072ae5517f969c5e10ef6ebe552be92`, `test/runtime-integration`; успішний CI [38156889236](https://github.com/trofoz/Word-Press-Woocommerce/actions/runs/38156889236), Classic/Blocks × HPOS off/on.

## 4. Контракт переходу та експлуатації

### Загальний контракт події завершення оплати

1. Для платної керованої покупки форк спершу надійно зберігає перевірений accepted receipt і фінансовий стан. Сторонній виклик `payment_complete()` без такого підтвердження не може завершити покупку.
2. Після прийняття надходження runner одноразово викликає штатний `WC_Order::payment_complete()` і відповідні події WooCommerce, зокрема `woocommerce_payment_complete`. Прийнята чинна оплата переводить замовлення у `completed` як для картки, так і для підтвердженого IBAN, незалежно від фізичного, віртуального або змішаного складу. Тип товару не визначає кінцевий статус; `processing` не потрібний. Вибір IBAN без підтвердження надходження лишає `on-hold`.
3. Повторний callback, повторне підтвердження того самого надходження або друга оплата не спричиняють повторного завершення замовлення чи повторної події оплати. Неоднозначні й пізні повідомлення проходять фінансовий review.
4. Фінансовий факт і результат виконання обліковуються окремо. Збій або невідомий результат після прийняття грошей лишається видимим у стані виконання та потребує контрольованого розгляду; автоматичного повтору всіх сторонніх hooks немає.
5. Чинна автоматизація FluentCRM споживає стандартне завершення WooCommerce. Плагін не додає окремої інтеграції Tutor/FluentCRM, не керує тегами, листами або Telegram. Приймання форку закінчується на підтвердженій оплаті, статусі та одноразовій події завершення.

### Legacy

1. Інвентаризувати старі callback URL, кожен `orderReference` формат, видані платіжні посилання, незавершені платежі й їхній строк. Не припускати, що всі reference мають один формат.
2. Кожну історичну спробу прив’язати до точного order, продавця, merchant account, ключа/версії конфігурації та callback route. Зберігати historical key захищено; поточний ключ не є автоматичним fallback.
3. Відсутній ключ або неоднозначне зіставлення — блок завершення переходу для цього платежу, видимий ручний розгляд. Не відкидати callback і не підтверджувати гроші неперевіреним підписом.
4. Перевірити новий handler при вимкненому оригінальному плагіні для точного перенесеного платежу. Невідомий reference не повинен породжувати нову оплату; зберегти retryable поведінку там, де власник старого handler ще потрібен.
5. Деактивація оригіналу дозволена лише після погодженого inventory та приймання всіх платежів, що лишаються в дорозі. Неперенесені/непотрібні історичні платежі мають явне закриття або legacy-оператора.

### Runner і спостережуваність

Код створює single event для виконання після оплати та щогодинну WP-Cron подію `wfpms_expire_purchases`; expiry обробляє пакет до 100 due records. Є order-level lock. WP-Cron не є точним таймером: shop traffic може затримувати події. Для staging/production потрібно зафіксувати system cron або інший підтримуваний runner, інтервал, блокування одночасного запуску, мінімальний пакет/повтор і власника сповіщень. Діагностика має показувати due backlog, вік найстарішої задачі, `execution_state=running` довше 900 секунд, останню помилку та кількість `needs_review`. Не запускати загальні cron hooks, якщо вони можуть виконати сторонні магазинні задачі; staging запуск має бути адресний до цього плагіна.

### Відкат

- **Відкат коду:** зупинити нові продажі/вимкнути нову видачу платіжних інструкцій, але зберегти сумісний handler для вже виданих callback, повернень і paid execution. Відновити попередній код лише після перевірки сумісності його схеми з новими записами.
- **Відновлення БД:** ніколи не повертати стару копію поверх нових оплат без зупинки продажів, експорту/збереження нових orders, receipts, refunds і callback доказів та їх фінансової звірки. Після резервної копії з новими надходженнями перевага — forward repair/reconciliation; повне DB restore лише за окремим планом, що відновлює всі подальші фінансові факти.
- **Практичний gate:** до staging install зберегти й перевірити backup, зазначити час/власника та відновлюваність. Production rollback окремо погоджує Надія; цей документ не є таким approval.

## Робочі потоки й власність

Спільний контракт для всіх потоків: гроші визнаються тільки після перевіреного receipt; кожне незалежне надходження зберігається; завершення order і подія оплати не повторюються; неоднозначні докази переходять у review; фінансовий snapshot order не підмінюється поточними реквізитами. Tutor і нова інтеграція FluentCRM поза вимогами плагіна; навчальна покупка завершується стандартною подією WooCommerce. Один інтегратор зводить гілки; один призначений оператор змінює staging. Під час цієї підготовки staging — read-only.

### Результат початкових паралельних аудитів

- **Платіжний код:** worktree чистий, змін не внесено. Статично перевірено, що archived seller блокує нову спробу зі старого `order-pay`, refund записується до конкретного receipt, а виконання планується після збереження accepted receipt. Кодова гілка `Refunded/Voided → Approved` переводить purchase у review, а не у paid; окремого regression сценарію для цієї послідовності немає. Через відсутність локального WP runtime не отримано red/green доказу й не змінювався production-код. Існуючий `php tests/unit-test.php` пройшов; callback/refund integration tests не запускались.
- **Legacy-перехід:** worktree чистий, змін не внесено. Код mapped callback звіряє merchant/signature з pinned `mapping.config_id`; недоступний historical key відхиляється без fallback. Unmapped callback повертає 503 без активного upstream handler. Runtime-тест із реально деактивованим upstream відсутній. Парсер/тести покривають numeric `{orderId}` і `{orderId}_woo_w4p_{n}`, але точний список виданих historical references не зберігається; точне звуження потребує рішення щодо migration data/schema. `php -l` пройшов для переглянутих legacy файлів; runtime не запускався.
- **Staging:** лише read-only WP-CLI перевірки. Fork уже активний поряд з Universal та legacy gateway. Page 15 — Classic shortcode у block-editor layout; WP-Cron expiry hook запланований щогодини. У перевірених product meta не знайдено очевидного Tutor/recurring ключа, але це не доводить відсутності course-side relation чи subscription. Backup, system runner і network isolation лишилися unknown. Подальші remote зміни не виконувались.

Порядок далі: інтеграція → CI на остаточному commit → один архів і SHA-256 → погоджене staging-приймання → перевірка без оригінального плагіна → окремо погоджений production cutover. Реальні платежі не є частиною цього підготовчого кроку.
