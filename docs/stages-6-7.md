# Етапи 6–7: IBAN, операторські рішення та Checkout Blocks

Дата: 10.10.2026. Реалізовано локально після етапів 1–5.

## Етап 6 — надходження та виконання

- Додано шлюз ручного переказу. Одне замовлення отримує незмінні інструкції з реквізитів конфігурації продавця: отримувач, податковий код, IBAN, банк, точна сума/валюта й призначення. Інструкції показуються на сторінці підтвердження, у деталях замовлення та email.
- Перша платіжна спроба фіксує строк у purchase. Початкові значення: 24 години для картки та 72 години для IBAN; адміністратор WooCommerce може налаштувати 1–720 годин. Поки попередня спроба має стан `issued`, інший канал для цього замовлення недоступний. Перемикання каналу не подовжує первинний строк.
- Додано адміністраторську форму обліку IBAN-надходження з банківським ID, фактичним рахунком, сумою, валютою й часом; оператор та час записуються в журнал подій. Точне своєчасне надходження на очікуване замовлення приймається автоматично. Дублі, конфліктні ID, інший рахунок/сума/валюта, пізні надходження та додаткові оплати залишаються для ручного розгляду.
- Повторний банківський ID не створює друге надходження. Повторне використання ID між замовленнями створює окрему подію review для другого замовлення з посиланням на первинну подію.
- Сторінка «WooCommerce → Платежі продавців» містить налаштування строків, вимикач нульових замовлень, форму надходження й чергу review. Операторське прийняття review-платежу вимагає перевірки можливості виконання й причини; рішення додається в event journal.
- Оператор може прийняти точне пізнє IBAN-надходження або підписаний `Approved` WayForPay receipt після перевірки незмінних реквізитів, стану замовлення й доступності виконання. Неповні/розбіжні або додаткові оплати не приймаються цією дією.
- Для дозволеної нульової суми зберігається підстава, не створюються спроби/надходження, а покупка передається стандартному `payment_complete()` WooCommerce.
- Після durable прийняття надходження runner викликає штатний `payment_complete()` один раз. Збій, невідомий підсумковий статус і завислий `running` переводяться у review; автоматичного повторного виконання немає. Підтвердження оператора лише закриває розгляд і не повторює хуки WooCommerce.
- Щогодинний WP-Cron переводить прострочені покупки до `expired`, зупиняє активні спроби й скасовує неоплачене Woo-замовлення через CRUD. Пізній платіж залишається окремим фінансовим фактом у review.

## Етап 7 — Checkout Blocks та сумісність

- Зареєстровано картковий і IBAN payment methods для WooCommerce Checkout Blocks; server-side `is_available()` використовує ті самі seller/config правила, що класичний checkout.
- Додано серверний захист змішаного кошика на додавання товару та перевірці checkout. Створене Store API замовлення проходить ту саму серверну фіналізацію, що й класичне.
- Увімкнено декларації сумісності WooCommerce для Checkout Blocks та HPOS. Дані order читаються/записуються через WooCommerce CRUD; прямого доступу до Woo orders/posts tables немає.
- Піднято схему plugin tables до версії 3. `Installer::maybe_upgrade()` застосовує `dbDelta` під час завантаження плагіна; існуючі фінансові записи не видаляються.

## Межі виконання

- Етапи 6–7 реалізовані локально, але не прийняті інтеграційно. PHP-середовище цього checkout не містить запущеного WordPress/WooCommerce, тому runtime поведінка payment gateway API, Checkout Blocks, WP-Cron, HPOS та `payment_complete()` тут не перевірена.
- Тести не додавалися й не запускалися. Не виконувались запити до WayForPay sandbox чи реального банку.
- Це не завершує весь блок етапів 7–8 із плану: автоматизована матриця Classic/Blocks × HPOS on/off, міграція історичних замовлень з upstream та підтвердження всіх 65 критеріїв PRD залишаються наступним інтеграційним етапом. Не заявляється сумісність із кожною версією WooCommerce лише на підставі декларації.
- WP-Cron обробляє строки з інтервалом запуску cron; це не точний таймер. Для магазину без регулярних запитів потрібен системний запуск WordPress cron за deployment-політикою.
- Штатне виконання WooCommerce може запускати сторонні інтеграції. Після невизначеного збою їхні ефекти звіряє оператор; плагін не має універсального replay LMS/CRM.
- P01–P03 та передрелізні умови з [етапів 4–5](stages-4-5.md) залишаються відкритими release gates.

Локальні перевірки цієї сесії обмежені PHP syntax lint і `git diff --check`; це не інтеграційне приймання.
