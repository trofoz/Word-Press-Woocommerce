# Етап 8 — міграція оригінального шлюзу

Дата: 10.10.2026. Реалізовано локально; інтеграційне приймання не виконувалось.

## Реалізовано

- Схему піднято до версії 4. Додана таблиця `wfpms_legacy_migrations` фіксує окреме явне зіставлення старого замовлення з purchase, продавцем і конкретною версією конфігурації.
- Сторінка «WooCommerce → Міграція WayForPay» показує старий `merchant_account`, наявність секрету без його значення та домен із `home_url()`. Адміністратор обирає вже заведений профіль і підтверджує відповідність мерчанта та домену. Секрет шифрується тим самим зовнішнім `WFPMS_MASTER_KEY`; старий option не видаляється.
- Повторний імпорт однакових реквізитів до того самого профілю є безпечним і не додає версію конфігурації. Зміна секрету чи домену створює нову версію, старі версії лишаються доступні для вже прив’язаних замовлень.
- Перелік показує до 100 неоплачених замовлень `pending`/`on-hold` зі способом оплати `wayforpay`. Кожне прив’язується окремою дією до продавця, в якого є імпортована конфігурація саме цього мерчанта. Категорії товарів не використовуються як доказ старого отримувача.
- Перехід розділений на два явні кроки. Спершу адміністратор готує callback route форку, але callback unmigrated legacy orders і далі обробляє оригінальний gateway. Після ручної прив’язки всіх відкритих неоплачених замовлень адміністратор окремо вмикає нові оплати.
- Міграція замовлення атомарно створює immutable purchase snapshot і запис прив’язки під тим самим order lock. Оплачені, скасовані, закриті, нульові та вже прив’язані замовлення не мігруються.
- Старий маршрут `wc-api=WC_wayforpay` нормалізується до hook `woocommerce_api_wc_wayforpay`. Після явної передачі маршруту адаптер перехоплює його перед upstream callback, приймає лише формат `orderId_woo_w4p_timestamp` і лише для запису міграції. Перевіряються підпис старого протоколу, merchantAccount і точна прив’язка reference. Сума та валюта збережені в receipt і мають збігтися зі знімком для операторського прийняття.
- Успішний старий callback завжди записується як `needs_review`: upstream не зберіг знімок початкової спроби, тому callback може бути повторною або пізньою оплатою. Він не викликає `payment_complete()` автоматично. Точне надходження може пройти наявний операторський перегляд; недоплату, переплату чи валюту, що не збігається зі знімком, не можна прийняти через цю дію.
- До явного підтвердження переходу нові gateway форку приховані. Після завершення cutover старий gateway `wayforpay` прибирається з доступних способів. Мігровані callback обробляє форк; невідомі йому валідні legacy reference передаються оригінальному gateway, який має лишатися активним.
- Після cutover адміністратор може окремо призупинити нові продажі. Пауза блокує checkout та серверне створення нових purchase, але зберігає оплату раніше зафіксованих замовлень, callback, expiry та execution.
- Операторська форма журналу повернень записує вже перевірений зовнішній refund як незмінну подію, з idempotency за receipt і refund ID та лімітом на gross receipt. Вона не відправляє кошти й не змінює стан доступу.

## Межі та залишкові перевірки

- Імпортуються тільки merchant account і secret key зі старого option. Адреса сайту не є підтвердженням домену: адміністратор має звірити та підтвердити його в кабінеті WayForPay.
- Універсальна база не визначає, кому юридично належало кожне старе замовлення. Замовлення без підтвердженої особи не мігрують; ручне призначення є обов’язковим.
- Старі оплачені замовлення не переписуються. Міграційний список охоплює лише відкриті неоплачені замовлення; completed/cancelled та інші статуси залишаються в WooCommerce без нового фінансового запису.
- Перехід опцій не є кнопкою відкату. Після початку нових оплат форк має залишатися активним для callback; деактивація плагіна не підтримує безперервність обробки.
- У середовищі немає WordPress/WooCommerce, Docker/Podman або MySQL-драйвера PHP. Нові сценарії паузи, передачі unmapped callback після cutover та запису refund event не пройшли runtime після останніх змін. Їх треба прогнати в матриці Classic/Blocks × HPOS; повний інтеграційний прогін залишається release gate.
- У налаштуваннях платежів адміністратор явно обирає сторонні gateway ID, дозволені для всіх продавців. Для призначеного кошика непозначені сторонні методи приховуються; кошик без чинного продавця не отримує сторонніх шлюзів. Погодження конкретного зовнішнього шлюзу для кожного продавця залишається відповідальністю магазину.
- До замовлень додано колонку та фільтр за продавцем для обох режимів списку WooCommerce: legacy orders і HPOS.
- У classic checkout і Checkout Blocks показується повне юридичне ім’я продавця, у тому числі якщо доступний лише дозволений сторонній gateway. У Blocks використано `IntegrationInterface` та слот `ExperimentalOrderMeta`.
- Локально пройшли unit/mock-тести маршрутизації простого товару, фільтра allowlist, реєстрації Checkout Blocks integration та передачі імені отримувача; пройшли PHP lint, Node syntax checks і `git diff --check`. Mock-тести перевіряють контракти, але не замінюють WordPress/WooCommerce runtime.
